## Bulldog Kernel – IDT Exceptions

Reviewed: November 2026

This document describes Bulldog's current exception-handling architecture, including exception routing through the IDT, fault processing, exception stack usage, and diagnostic behavior.

It reflects the implementation found in:

    kernel/src/interrupts.rs
    kernel/src/gdt.rs

It complements:

    interrupts.md
    interrupts-implementation.md
    gdt.md
    paging.md
    processes.md

This document describes the current implementation rather than future exception-handling plans.

---

## 1. Overview

Exceptions are synchronous events generated by the CPU while executing instructions.

Bulldog installs exception handlers during early kernel initialization.

Current exception handlers:

    Receive InterruptStackFrame
    Log diagnostic information
    Log error codes where available
    Log faulting addresses where applicable
    Panic the kernel

Current exception handling is intentionally diagnostic-focused.

Process-level exception recovery is not currently implemented.

---

## 2. Exception Categories

### Faults

May theoretically be recoverable if the underlying condition is corrected.

Examples:

    Page Fault
    General Protection Fault
    Invalid Opcode

Current Bulldog behavior:

    Log diagnostics
    Panic

---

### Traps

Reported after instruction execution.

Examples:

    Debug
    Breakpoint
    Overflow

Current Bulldog behavior:

    Log diagnostics

or

    Log diagnostics and panic

depending on handler type.

---

### Aborts

Severe processor failures that cannot be safely recovered.

Examples:

    Double Fault
    Machine Check

Current Bulldog behavior:

    Log diagnostics
    Panic

## 4. Exception Frames

The CPU automatically constructs an exception frame before invoking an exception handler.

Typical contents include:

    RIP
    CS
    RFLAGS
    RSP
    SS

Certain exceptions additionally provide:

    Error Codes

All Bulldog exception handlers receive:

    InterruptStackFrame

and use it for diagnostics.

Current handlers log:

    Exception type
    Stack frame
    Error code (if present)

before fault termination.

---

## 5. Page Fault Handling

Page faults are handled by:

    page_fault_handler()

Current diagnostics include:

    Faulting Address (CR2)
    PageFaultErrorCode
    InterruptStackFrame

Typical logged information:

    Accessed address
    Error code
    Processor state

After logging:

    Kernel panic

Current implementation does not attempt recovery.

Page faults currently execute on:

    IST1

using the LAPIC/Page-Fault stack.

---

## 6. Page Fault Error Information

Current page-fault handling records:

    Present bit violations
    Write-access faults
    User-access faults
    Reserved-bit violations
    Instruction-fetch faults

through:

    PageFaultErrorCode

This information assists kernel debugging and memory-management development.

---

## 7. Double Fault Handling

Double faults are handled by:

    double_fault_handler()

Current characteristics:

    Dedicated IST stack
    Dedicated IDT entry
    Diagnostic logging
    Immediate kernel panic

Double faults are treated as unrecoverable failures.

---

## 8. IST Usage

Bulldog currently uses dedicated interrupt stacks for critical exception paths.

### IST0

Used for:

    Double Fault

Purpose:

    Survive stack corruption
    Survive fault recursion

---

### IST1

Used for:

    Page Fault
    LAPIC Timer

Purpose:

    Fault isolation
    Timer reliability

This arrangement reduces dependence on the interrupted execution stack.
